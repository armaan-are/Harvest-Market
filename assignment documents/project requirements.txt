System Overview
The platform serves as a local marketplace connecting community members ("Neighbors") with
local small-scale producers ("Farmers"). You will build a three tier web application to support
this system. Development will be based on an existing prototype that provides core
functionality, architectural fundamentals, and reference implementations. The prototype is
missing some important features and techniques that this project is expected to use, but it still
provides a solid foundation for your work.
Starter code and documentation are available at:
https://github.uconn.edu/CSE2102-Spring26/local-farm-exchange.git
Core Functional Requirements
• User Management & Security
o Dual Roles: The system must support two distinct user types: Neighbors (Buyers)
and Farmers (Sellers).
o Secure Authentication: Users must be able to securely register and log in.
Purchasing capabilities must be restricted exclusively to logged-in users.
o Neighbor Profiles: Buyers must have a profile that stores contact information
and a default "Home Location" (Zip Code) to facilitate local search.
o Farm Profiles: Sellers must have a public profile displaying their Farm Name,
Biography, Pickup Address, and Operating Hours.
o Role Isolation: The system must ensure Buyers cannot access Farmer
management dashboards.
• Marketplace Inventory & Discovery
o Inventory Management: Farmers must be able to Create, Read, Update, and
Delete (CRUD) product listings.
o Image Handling: Listings must support actual image file uploads to display
products (replacing text-based URL links).
o Categorization: Products must be organized by tags such as Produce, Dairy,
Meat, and Baked Goods.
o Location Filtering: The search results must be filterable by location, allowing
buyers to see only products within a specific zip code or radius.
• Transaction Engine (Order Lifecycle)
o Non-Instant Orders: Unlike standard e-commerce, orders must not be instant.
They must follow a strict approval lifecycle:
§ Pending: Inventory is reserved ("soft lock") while waiting for approval.
§ Confirmed: Farmer accepts the request; inventory is permanently
deducted.
§ Ready for Pickup: Farmer notifies the buyer that items are packed.
§ Completed: Transaction is closed after the physical pickup occurs.
o dashboards:
§ Buyer View: A "My Orders" dashboard to track the status of active and
past purchases.
§ Farmer View: An "Incoming Requests" queue to Approve or Reject
orders.
o Cancellation Logic: If an order is rejected or cancelled, the system must
automatically release the reserved inventory back to the listing.
• Community & Trust
o Contextual Messaging: A private chat/message system that allows Buyers and
Sellers to communicate, specifically linked to a product or order context.
o Verified Reviews: Buyers must be able to rate Farmers (1-5 stars) and leave
comments.
o Review Constraint: To prevent fraud, the system must restrict reviews so they
can only be submitted after a transaction has reached the "Completed" state.
Optional & Advanced Features
• AI-Powered Discovery: An intelligent recommendation engine that suggests products
based on semantic similarity (e.g., suggesting "Beeswax Candles" to a user viewing
"Honey") rather than just keyword matching.
• Pickup Scheduling: A system requiring buyers to select a specific time slot (e.g.,
"Saturday 9:00–9:15 AM") during checkout to prevent overcrowding at the farm.
• Dynamic Pricing: Automated logic that applies discounts to perishable items as they
approach their expiration date.
• Subscription Models (CSA): Support for recurring "Community Supported Agriculture"
subscriptions, allowing buyers to sign up for weekly box pickups rather than one-time
purchases.
